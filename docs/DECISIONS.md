# DECISIONS

Things examined, found correct or deliberate, and **not to be re-raised**. If a
future session rediscovers one of these as a "bug", the answer is here.

*Last updated: 2026-08-29*

| # | finding | verdict | reasoning |
|---|---|---|---|
| 1 | `latest/` and `stable/` duplicate every file in `image-files/` | by design | They are build outputs of `update.sh`, committed so the Docker build context is self-contained and a tag is reproducible. Edit `image-files/` only. |
| 2 | `IBC_VERSION` may differ between `Dockerfile.template` and the channel Dockerfiles | by design | `detect-ibc-release.yml` bumps the templates only and deliberately skips `update.sh`; the next IB Gateway release propagates it. Comment is in the workflow. The gap seen on 2026-08-25 (templates `3.24.1`, `latest/` `3.24.0`, `stable/` `3.23.0`) was closed the same day by regenerating both channels on request; it reopened at the next IBC bump, as expected, and as of 2026-08-28 reads templates `3.24.2`, `latest/` `3.24.2`, `stable/` `3.24.1`. The README reports each channel's own number rather than one for both — see #26. |
| 3 | `README.md` duplicates `template_README.md` | by design | `README.md` is generated by `envsubst` in `detect-releases.yml`. Edit the template. |
| 4 | Published host ports map to 4003/4004, not the documented API ports 4001/4002 | correct | `set_ports()` binds the API to container loopback and socat forwards it. Documented in `CLAUDE.md` and `docs/RUNBOOK.md`. |
| 5 | `dotenv-linter:latest` reports ~29 `UnorderedKey` findings on `.env-dist` | not a defect | The pinned pre-commit hook is `0.5.0`; the Docker image is 3.x and stricter. `.env-dist` is grouped by service and by concern so it reads as the key list for both compose files; alphabetising would scatter each service's keys to satisfy a linter the repository does not run. |
| 6 | `stop_ibc()` in `run.sh` uses broad `pkill` patterns | correct in context | It runs **inside** the container, where those patterns match only its own children. The rule against broad `pkill` applies to the host. |
| 7 | `MD013` (line length) is disabled in `.markdownlint.yaml` | deliberate | `README.md` is generated from `template_README.md`, and most long lines are option tables whose width their content sets. Any manual reflow is undone at the next release. Decided 2026-08-25. |
| 8 | `bastion/Dockerfile` carries `# hadolint ignore=DL3025` | deliberate | The healthcheck uses bash `/dev/tcp` redirection, which JSON exec form cannot express. Rewriting it would change behaviour to satisfy a style rule. Decided 2026-08-25. |
| 9 | `MD036` (emphasis-as-heading) is disabled in `.markdownlint.yaml` | deliberate | `CLAUDE.md` prescribes a `*Last updated: YYYY-MM-DD*` vintage line under headings throughout `docs/`. That is metadata, not a heading, and the rule cannot tell them apart. Decided 2026-08-25. |
| 10 | A change to `image-files/` was propagated by copying into `latest/`/`stable/` instead of running `update.sh` | deliberate | `update.sh` also regenerates the channel Dockerfiles, which would have pulled `IBC_VERSION` 3.24.1 into both channels - bumping `stable` from 3.23.0 ahead of its release cycle. Copying the changed scripts keeps the `image-files == latest == stable` invariant for scripts while leaving the version drift in #2 intact. Decided 2026-08-25. |
| 11 | The `tests/container` suite is not run in CI | deliberate | The gateway image `build.yml` produces is multi-platform and lands in the job-local registry, never in the runner's own Docker daemon, so `tests/run.sh container` has nothing to start without an extra single-platform load. That would add a build leg for a property the unit suite already pins at the script level. Run it locally after touching `run.sh`, `common.sh` or `run_socat.sh`. Decided 2026-08-25, reasoning restated 2026-08-25 when the registry replaced `push: false`. |
| 12 | `stable` ships IBC `3.24.1`, the same as `latest`, rather than an older IBC | deliberate, 2026-08-25 | Regenerating both channels was requested so the new `IBC_SHA256` verification would reach the published images now rather than at the next release. It moved `stable` from IBC `3.23.0`. Both channels were then built locally and both checksum steps reported `OK`. |
| 13 | `tws-docker-compose.yml` is gone; `docker-compose.yml` holds both applications behind Compose profiles | deliberate, 2026-08-25 | Requested: one compose file, with `.env` naming the image to run. Profiles keep each service's own `devices`/`shm_size`/`security_opt`, volume set and container-side ports intact, which a single merged service could not — `/dev/dri` is mandatory for `tws` and fails on a host without it, and `$HOME` differs (`/config` vs `/home/ibgateway`), so the SSH mount path cannot be shared. `IB_APP` in `.env` feeds `COMPOSE_PROFILES`, which is the only name Compose reads. The TWS host ports were renamed `PORT_HOST_RDESKTOP_*` so both services can be selected at once without a collision. Pinned by `tests/unit/compose.bats`. |
| 14 | `Dockerfile.template` picks the IB installer by architecture and downloads no JRE of its own | fix, 2026-08-25 | Each IB installer bundles the JRE for its own architecture, so the x64 one cannot install on aarch64: it unpacks an x86-64 `java` and dies with `jre/bin/java: not found` (exit 127 natively, 255 under QEMU). The previous code downloaded an aarch64 Zulu JRE and passed `app_java_home` to redirect the installer; that variable is not honoured, so the Zulu download was verified, shipped and then ignored while the build failed anyway. Selecting `…-standalone-linux-arm.sh` on aarch64 fixes it and removes the Zulu download and its pinned `ZULU_SHA256`. Reproduced and verified locally on `linux/arm64`, 2026-08-25. **`COPY --from=setup /usr/local/` stays** — see #18 below; it was removed with Zulu on the mistaken belief that it only carried Zulu, and restored the same day. |
| 15 | `build.yml` runs a `registry:2` service and pushes the gateway image to `localhost:5000` | deliberate, 2026-08-25; reason narrowed 2026-08-29 | `Dockerfile.tws` builds FROM the gateway image, which was not anonymously pullable until the packages went public — see #32, which removes the original reason: the TWS leg used to fail with `403 Forbidden` from the ghcr token endpoint. The decision stands on the two reasons that remain. Handing the job registry credentials would be worse on both counts: a PR build would gain push-capable secrets, and it would verify the TWS image against whatever ghcr already holds rather than against the gateway image built in the same run — and for a version-bump PR that tag does not exist yet at all. The job-local registry keeps `permissions: contents: read`, needs no secret, and dies with the job. |
| 16 | The three callers of `build.yml` use `uses: ./.github/workflows/build.yml` | deliberate, 2026-08-25 | They were pinned to `dennisdeh/ib-docker/.github/workflows/build.yml@master`, so a branch run executed **master's** copy of the build, not the branch's. A change to `build.yml` was therefore untestable before merge, and the same commit could pass on a branch and fail on `master` — which is exactly what happened to `257d7477` on 2026-08-25 (branch green at 08:48, `master` red at 08:50, same SHA). The local path resolves to the calling run's own ref. |
| 17 | Nothing in this repository consults the project it was forked from | deliberate, 2026-08-25 | Requested by the owner. The relationship is credit only — `LICENSE` and the README — and no remote, check, schedule, version comparison or investigation step depends on it. The image's real upstreams are Interactive Brokers' installer servers, `IbcAlpha/IBC` and `lscr.io/linuxserver/rdesktop`, and those are the only external projects any workflow reads. |
| 18 | `Dockerfile` and `Dockerfile.tws` copy the whole of `/usr/local` out of the setup stage | required, 2026-08-25 | It carries the JVM. The IB installer unpacks its JRE to `/usr/local/i4j_jres/<id>/<version>-zulu` and writes that absolute path into the install directory's `.install4j/pref_jre.cfg`, which is what the `ibgateway` launcher reads — so without the copy the image contains a launcher pointing at a JVM that is not there, and nothing fails until IBC tries to start. Where the JRE lands varies: `latest@10.48.1e` on aarch64 puts one inside the install directory as well, `stable@10.45.1j` puts it only under `/usr/local` on both architectures — so testing one channel proves nothing about the other. It was deleted on 2026-08-25 after checking `/usr/local` on a bare `ubuntu:24.04` instead of on the setup stage, which shipped two JVM-less images; restored the same day, and both Dockerfiles now end their runtime stage with a `find … -name java` + `java -version` check so the build fails instead. Verified by deleting the copy and watching that step exit 1. |
| 19 | `detect-releases.yml` publishes by **calling** `publish.yml`, not by pushing a `v<version>-<channel>` tag | forced, 2026-08-26 | A tag pushed with `GITHUB_TOKEN` does not start a workflow run — GitHub's own loop prevention. "Tag it and let `publish.yml` notice" therefore publishes **nothing**, and reports success while doing it, which is the worst available failure. `workflow_call` needs no token and no PAT. The tag path stays for a release made by hand. Pinned by `tests/unit/workflows.bats`. |
| 20 | The images for a new IB version are published from the **release bot's commit**, before its PR is merged | deliberate, 2026-08-26 | The ask was for detection to reach `ghcr.io` with no human step; waiting for a merge puts the manual step straight back. The bot commit is `master` plus the deterministic output of `update.sh` and `envsubst`, i.e. byte for byte what merging would have published. Publishing an image tag is also far less invasive than the alternative — a bot with rights to auto-merge its own PRs into `master`. The PR still gets its human review, and `org.opencontainers.image.revision` on the image records the exact commit built. |
| 21 | Docker Hub is skipped when its secrets are unset, while `ghcr.io` never is | deliberate, 2026-08-26 | `ghcr.io` is the registry this repository owns and authenticates to with the run's own `GITHUB_TOKEN`. Docker Hub needs `DOCKERHUB_USERNAME`/`DOCKERHUB_TOKEN`, which a fork cannot hold; an unconditional `docker/login-action` against it fails the whole publish over a mirror. |
| 22 | The bastion image is published from `publish.yml`, tagged with its own `ARG IMAGE_VERSION` rather than an IB version | deliberate, 2026-08-27 | Requested: publish it alongside the other two, so a host can be provisioned entirely from published images. The bastion carries no IB version — it is the ssh jump host, and it changes on its own schedule — so an IB version would be a meaningless tag on it. Its Dockerfile declares the version, which is the same shape as reading `ENV IB_GATEWAY_VERSION` from a channel Dockerfile and keeps one place to bump. Publishing rides on `publish.yml` rather than a workflow of its own because that is the only path already holding `packages: write`; the cost is re-pushing an unchanged image on every IB release, which is layer-deduplicated. Re-publishing the same `IMAGE_VERSION` after a base-image refresh overwrites that tag on purpose. |
| 23 | `deploy/provision.sh` still builds the bastion when it cannot pull it | deliberate, 2026-08-27; reason narrowed 2026-08-29 | A freshly bumped `IMAGE_VERSION` has no published tag until the next release, and a host may have no route to ghcr.io at all; failing there would strand provisioning on either. The package being private was a third reason and is gone — see #32; the pull now needs no credentials. The fallback needs `bastion/`, which is the one thing the script still wants a checkout for. |
| 24 | The repository is named `ib-docker`, while the images keep their own names | deliberate, 2026-08-27 | Requested. One `docker-compose.yml` runs IB Gateway, TWS and the bastion behind profiles, so `ib-gateway-docker` named one of three things it ships. The **packages were not renamed**: `ghcr.io/dennisdeh/ib-gateway`, `tws-rdesktop` and `bastion` are what users pull and what `Dockerfile.tws` opens `FROM`, a ghcr package does not follow a repository rename, and every published tag would have to be re-pushed. Two occurrences of the old string are kept on purpose — `gnzsnz/ib-gateway-docker` (credit, and not ours to rename) and the Investio vendored directory (not in this tree). Pinned by `tests/unit/naming.bats`. |
| 25 | The rename must land on GitHub before this branch merges | ordering, 2026-08-27 | `Dockerfile.template` downloads the IB installers from `https://github.com/dennisdeh/<repo>/releases/download/...` with `curl -f`, so the new URL 404s until the repository is actually renamed and every build fails at that step. GitHub redirects the *old* URL to the new one after a rename, never the other way round, so renaming first is safe and merging first is not. There is no `gh` here, so the rename is a browser action for the owner. |
| 27 | `lscr.io/linuxserver/rdesktop` stays a third-party base rather than being rebuilt here | deliberate, 2026-08-28 | Audited on request: everything the stack *runs* is one of the three images this repository builds and publishes, and every compose file it ships builds all three from this checkout. The only third-party image inside anything published is the xrdp/xfce desktop the TWS image adds TWS to; `ubuntu` and `bats/bats` are the others, and `bats/bats` never ships. Forking a whole desktop base to own it would be a large maintenance surface for no security or reproducibility gain that pinning does not already give. The decision is recorded as an allowlist in `tests/unit/images.bats`, so a *new* third-party base is a deliberate edit to that list rather than a diff nobody reads, and Dependabot now watches every directory that holds a Dockerfile — see `OPEN_ITEMS.md` #13. |
| 26 | `README.md`'s Supported Tags table reads IBC per channel, from the channel Dockerfiles | fix, 2026-08-28 | It read one `IBC_VERSION` out of `Dockerfile.template` and printed it on every row. That is right only while the channels agree, and #2 says they routinely do not: on 2026-08-28 the table claimed `stable` shipped IBC `3.24.2` when the image contains `3.24.1`. `detect-releases.yml` now exports `LATEST_IBC`/`STABLE_IBC` from `latest/Dockerfile` and `stable/Dockerfile` — the same files the version columns already come from — plus `BASTION_VERSION` from `bastion/Dockerfile`, so the bastion row names a tag too. `tests/unit/naming.bats` reproduces the substitution and diffs the committed README, which the extra variables make deterministic: the old check had to accept any of three IBC values because the template's number and the channels' could legitimately differ. |
| 28 | `on-push-n-pr.yml` filters the release bots with a `github.head_ref` check on the job, not with `'!update-*-to-*'` / `'!IBC-update*'` under `pull_request.branches` | correction, not a loosening | For `pull_request` that filter matches the **base** branch, which is always `master` here, so the negations excluded nothing — release-bot PRs did run CI and then sat at `action_required`. `head_ref` is the only place the exclusion can work. The `push` trigger keeps its negative patterns, where they do match the pushed branch. |
| 29 | The branch globs in `on-push-n-pr.yml` and `lint.yml` are `'**'`, not `'*'` | fix, 2026-08-25 | A single `*` does not match `/`, so no branch with a slash in its name — the usual `feature/…` convention, and the `claude/…` names this repository actually uses — ever triggered CI or lint. `'**'` matches across separators; the negative patterns beside it are unaffected. |
| 30 | `docker compose build --pull tws` is still the wrong command, for a new reason | corrected, 2026-08-29 | Until the packages went public that day (#32) it could not work at all: `--pull` means "fetch the base from the registry every time", and the base needed credentials this build deliberately does not have. It now succeeds — which is worse, because it silently resolves `ghcr.io/dennisdeh/ib-gateway:latest` from the registry instead of the gateway image the previous command just built, so what gets verified is whatever the last release published. The sequence is unchanged: `docker compose build ib-gateway` then `docker compose build tws`, without `--pull` on the second. The build args that make that work landed on 2026-08-25 and were re-verified on 2026-08-29 by building the tws `setup` stage alone, which resolved `IB_GATEWAY_BASE_IMAGE=ghcr.io/dennisdeh/ib-gateway` / `IB_VERSION=latest` against the image `docker compose build ib-gateway` had just produced, with no `docker tag` and no registry access. `OPEN_ITEMS.md` #16 records the workaround era. |
| 31 | `MD060` (table-column-style) is disabled in `.markdownlint.yaml` | deliberate, 2026-08-29 | It arrived with markdownlint-cli 0.49 during the hook update of `OPEN_ITEMS.md` #23 and fires 228 times, every one of them padding inside table pipes. Same case as `MD013` in #7: the tables are in `README.md`, which is generated, so a hand-reflow is undone at the next IB Gateway release, and the rule judges how a table is spelled rather than whether it renders. Every other hook passes at the updated revisions. |
| 32 | The three ghcr.io packages are public | measured, 2026-08-29 | `ib-gateway`, `tws-rdesktop` and `bastion` each answer an anonymous pull: with a token fetched from `ghcr.io/token` with no credentials, all three return 200 for `manifests/latest` and a full `tags/list`, and the gateway's `linux/amd64` config blob downloads — a real pull, not a manifest peek — on a machine with no `~/.docker/config.json` at all. The repository is public with it (`"private": false`), so the IB installers a rebuild needs are reachable too. They were private when the 2026-08-25 sweep measured them, and four days later a dozen comments and instructions across the tree still said so, which is what this row exists to stop: #15, #23 and #30 point here rather than each restating the fact. `tests/unit/images.bats` fails on any file that tells a reader to log in to ghcr.io before pulling — the instruction half of that drift, and the half a grep can hold; the reasoning half lives here. Should the packages ever go private again, rewrite this row and that test in the same commit. |
| 33 | The bastion image declares `Apache-2.0` while the other two declare `MIT` | correct, 2026-08-30 | Not a mismatch to be tidied away. `LICENSE` at the root is MIT and governs the tree the gateway and TWS images are built from; `bastion/` is a fork that vendors its upstream's Apache-2.0 `LICENSE.txt`, which is what its files are under. The two labels had been swapped, each carrying the other's licence — `OPEN_ITEMS.md` #28. Because `docker/metadata-action` derives `org.opencontainers.image.licenses` from the *repository* and applies its labels over anything the Dockerfile set, the bastion's value has to be repeated in `publish.yml`'s bastion meta step; the gateway and TWS need no such line, the derived value being already right for them. The label names the licence of this repository's own contents — the third-party software the images install, IB Gateway (proprietary) and IBC (GPL-3.0), is not what it is describing, and a fuller SPDX expression saying so would be a deliberate change rather than a correction. |
